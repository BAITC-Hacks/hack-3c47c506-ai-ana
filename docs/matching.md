# Подбор и диагностика: этап 4

Подбор реализован как отдельная функция `recommend(query, catalog)` в `backend/app/matching.py`. Она не зависит от браузера, HTTP, текущего времени или внешнего AI. На этом этапе результат доступен в Python и через CLI; публичные карточки с объяснениями и API относятся к этапу 5.

## Запрос

Обязательные поля: `city`, `event_date`, `event_format`, `category`, `budget_kzt`. Необязательные: `duration_hours`, `language`.

Бюджет — положительное целое число тенге. Строки, дробные значения, логические значения, ноль, отрицательные числа, NaN и бесконечность отклоняются. Длительность — положительное конечное число, включая дробные часы; внутри используется Decimal. Необязательное пустое поле, строка из пробелов или null снимают соответствующее условие. Непустая числовая строка длительности не подменяется числом автоматически.

Дата — календарная ISO-дата в диапазоне 23.09.2026–31.12.2026 включительно. Время, часовой пояс, Unix timestamp и даты вне окна не принимаются. Для прямого вызова Python допустим объект date, но не datetime. Окно не привязано к сегодняшнему дню.

Текстовые условия проверяются по словарям всего загруженного каталога. Нормализация сравнения совпадает с загрузчиком: Unicode NFKC, свёртка пробелов, casefold. Нечёткие совпадения и неявные алиасы отсутствуют. В нормализованном запросе используется стабильная подпись из каталога; исходные профили не изменяются.

Неизвестный город/формат/язык/категория — `QueryValidationError` с полем и причиной, а не бизнес-исход пустой выдачи. Уже созданная модель запроса также повторно валидируется: передача объекта не обходит проверки.

## Фильтры и порядок

Сначала выбирается группа по совпадению города и вхождению выбранной категории в categories. Каждый профиль учитывается один раз. В этой группе обязательны:

1. Отсутствие запрошенной даты в busy_dates.
2. Поддержка event_format.
3. Начальная цена не выше бюджета.
4. Поддержка language, если он задан.
5. Лимит max_hours не ниже duration_hours, если оба значения заданы.

Площадки проходят те же проверки занятости. null-длительность услуги не ограничивает запрос по часам, но не означает обещание неограниченной работы. Описание не расширяет географию, форматы или языки и не компенсирует нарушенные условия. Дополнительные ограничения из текста нужно будет показывать в объяснениях на следующем этапе, без скрытого изменения этих фильтров.

Все прошедшие сортируются по `(price_from_kzt, normalize_key(id))`. Только после полной фильтрации и сортировки берутся первые три. Синтетичность, дополнение цены/города и происхождение не меняют порядок. Это приоритет меньшей начальной цены, а не оценка качества исполнителя.

Версия правил: `price-asc-canonical-id-v1`. Она сопровождает каждый результат вместе с catalog_version. Изменение фильтров, приоритета причин или порядка требует пересмотра этой версии.

## Исходы и диагностика

- `MATCHED`: есть хотя бы один прошедший кандидат; возвращаются от одного до трёх.
- `CATEGORY_UNAVAILABLE`: группа города и категории пуста, хотя каждое значение известно словарям каталога.
- `NO_MATCHES`: группа есть, но все профили исключены.

В результате содержатся нормализованный запрос, статус, итоговый русский текст, counts (group/matched/shown), matches (до трёх исходных профилей), eligible_ids (все прошедшие в стабильном порядке), exclusions и rejections. Объяснения отдельных карточек пока отсутствуют.

Для каждого исключённого профиля сохраняются все причины в фиксированном порядке:

```text
BUSY_ON_DATE → UNSUPPORTED_FORMAT → OVER_BUDGET → UNSUPPORTED_LANGUAGE → DURATION_EXCEEDED
```

Первая причина основная; только она увеличивает общий счётчик. Нулевые счётчики тоже присутствуют. Равенство:

```text
counts.group = counts.matched + sum(rejections.values())
counts.shown = min(3, counts.matched)
```

Отобранные и исключённые записи имеют стабильный порядок. В сообщении объясняется количество: например, в небольшой группе все проходят либо часть исключена по конкретным условиям. Не добавляются записи из другого города или категории.

## Воспроизведение без API

Из папки `backend/`:

```bash
.venv/bin/python -m app.match_cli --query docs/queries/corporate-host.json
.venv/bin/python -m app.match_cli --query docs/queries/corporate-host-next-date.json
.venv/bin/python -m app.match_cli --query docs/queries/no-matches.json
.venv/bin/python -m app.match_cli --query docs/queries/no-category.json
```

Все относительные пути CLI отсчитываются от корня проекта. Для проверки производного JSONL:

```bash
.venv/bin/python -m app.match_cli --query docs/queries/corporate-host.json --catalog data/derived/catalog.jsonl
```

CLI использует exit code 0 для всех трёх бизнес-исходов. Ошибка запроса или каталога — exit code 1 и JSON в stderr с кодом INVALID_QUERY или CATALOG_LOAD_FAILED. Это внутренний диагностический вывод, не контракт будущего API. В нём Decimal сериализуется точной канонической строкой (например, `"1e1"` означает 10), цена — JSON integer, даты — ISO, отсутствующие условия — null. Исходные описания в matches остаются данными профилей; это не готовые объяснения для пользователя.

## Проверки

Проверены границы цены, длительности и календаря, null, многокатегорийность, площадки, нормализация, недопустимые запросы, приоритет причин, сохранение флагов и случаи 1/2/3/более 3 результатов. Отдельно проверены расхождения текстов с полями исходных профилей.

Детерминизм проверяется по полному сериализованному результату, включая сообщения, причины и длительности: повтор запроса, перестановка CSV/JSONL и самого Catalog.profiles, равные цены, эквивалентная запись Decimal, новые процессы с разными PYTHONHASHSEED. Обнаруженное расхождение сериализации 10 и 1E+1 устранено без потери точности.

Итоговый прогон всех серверных тестов зафиксирован в [progress.md](progress.md). Интерфейс, endpoint рекомендаций и объяснения отдельных карточек этим этапом ещё не проверяются.
