# Как разместить CSV нашего проекта в облаке

Это рекомендации, без реализации. Облачные ресурсы не созданы, файл никуда не загружен, код и настройки приложения не изменены. Документ подготовлен 23.09.2026.

## Что я рекомендую для нашего проекта

Для первого размещения сайта я бы положил CSV **на постоянный диск облачного сервера, где работает FastAPI**. Это самый простой вариант для текущей архитектуры: существующий загрузчик уже умеет читать такой файл.

Если нужно хранить каталог отдельно от сервера и обновлять его независимо от выпуска приложения, я бы выбрал **приватное объектное хранилище**, например Cloudflare R2. Сервер скачивал бы выбранную версию CSV перед запуском. Этот шаг загрузки ещё потребуется организовать.

Наш файл содержит 66 профилей и занимает около 98 КБ. Для такого каталога основная задача — удобное обновление и сохранность данных. Переходить на базу данных только ради переноса файла в облако сейчас необязательно.

## Вариант 1. CSV на диске облачного сервера

Облачный сервер — это удалённый компьютер, на котором можно запустить наш Python-backend и хранить файл.

Предполагаемый порядок:

1. Выбрать сервер для FastAPI с постоянным диском.
2. Разместить на нём backend и копию исходного CSV.
3. Дать процессу backend право читать файл.
4. Указать путь через уже существующую переменную `CATALOG_PATH`.
5. Запустить backend и подключить сайт к его API.

Пример будущего значения, которое сейчас **не применялось**:

```dotenv
CATALOG_PATH=/srv/ai-ana/data/catalog.csv
```

Путь приведён как пример: такого каталога на сервере мы пока не создавали. При сохранении исходного содержимого переименование копии файла не меняет сам набор профилей.

**Плюс:** Python-код загрузчика менять не нужно. **Компромисс:** обновлять CSV и хранить резервные копии придётся организованно; файл привязан к диску сервера.

Если backend работает в контейнере, для изменяемого CSV нужен подключённый постоянный диск или том. Сохранение файла только внутри временного контейнера не подходит для каталога, который должен переживать пересоздание этого контейнера.

## Вариант 2. CSV в отдельном облачном хранилище

Объектное хранилище хранит файлы в контейнерах, которые обычно называют bucket. CSV остаётся обычным файлом: каждая строка не превращается автоматически в запись базы данных.

| Сервис | Возможности, полезные для нашего случая | Когда рассмотреть |
|---|---|---|
| Cloudflare R2 | Хранение объектов и доступ через S3-совместимый API. [Документация](https://developers.cloudflare.com/r2/api/s3/) | Если нужен отдельный файловый каталог без перехода на БД |
| Supabase Storage | Приватные buckets и доступ по авторизации либо временной подписанной ссылке. [Документация](https://supabase.com/docs/guides/storage/buckets/fundamentals) | Если дальше планируем использовать другие возможности Supabase |
| Amazon S3 | Объектное хранилище с управлением доступом и версионированием. [Документация](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html) | Если backend и остальные ресурсы размещаются в AWS |

Выбор R2 здесь — моя рекомендация по разделению файла и сервера, а не результат сравнения тарифов или скорости. Не стоит выбирать целую платформу только ради небольшого CSV, если уже есть подходящий сервер или облачный аккаунт.

Предлагаемая схема:

```mermaid
flowchart LR
    Storage["Приватное хранилище CSV"] -->|"Загрузка перед запуском"| File["Локальная копия на сервере"]
    File -->|"Чтение и валидация"| API["FastAPI: каталог в памяти"]
    Site["Наш сайт"] -->|"Параметры события"| API
    API -->|"Карточки и основания"| Site
```

Сначала сервер получает файл, проверяет его и загружает каталог в память. Запросы пользователей работают с уже загруженными данными. Скачивать CSV из облака при каждом нажатии «Подобрать подрядчиков» я бы не стал: это добавляет задержку и зависимость каждого запроса от хранилища.

Для R2 можно выдать серверу доступ только на чтение объектов нужного bucket. Ключи доступа должны храниться на стороне сервера или в секретах хостинга; в React-код и Git их помещать не нужно. Возможности ограничения токенов описаны в [документации R2](https://developers.cloudflare.com/r2/api/tokens/).

Временная подписанная ссылка подходит для разовой загрузки, но не как бессрочный адрес каталога в настройках: она истекает. Для регулярной работы лучше серверная авторизация. Подписанная ссылка даёт доступ её обладателю до окончания срока. [Описание механизма R2](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

## Что важно именно в нашем приложении

- **`CATALOG_PATH` сейчас принимает путь к файлу, а не интернет-ссылку.** Просто подставить `https://…` или `s3://…` не получится. Для объектного хранилища нужен отдельный шаг скачивания либо доработка загрузчика. Первый способ позволяет сохранить текущий Python-код.
- **Файл читается при запуске backend.** Замена CSV на диске или в bucket сама по себе не обновит карточки. В простом варианте после обновления нужен перезапуск всех экземпляров backend с одной выбранной версией.
- **Сайт уже работает через API.** Ему не нужно напрямую скачивать CSV или получать ключ от bucket. Само хранилище также не заменяет сервер FastAPI: для работы подбора сервер всё равно должен быть доступен.
- **Перенос не меняет происхождение.** Для предоставленного CSV остаётся `original`; облачное размещение не превращает профили в добавленные командой.
- **Неизменённый CSV сохраняет версии данных.** Если поменять содержание, может измениться `catalog_version` и результат подбора. Версию можно смотреть в `/health` и `/api/catalog/meta`.
- **Объяснения связаны с описаниями.** Файл `backend/app/data/profile_facts.json` размечен для текущих профилей. После изменения описаний или добавления новых записей часть карточек получит структурированные основания с предупреждением вместо прежней цитаты. Для новых индивидуальных фактов потребуется обновить разметку.
- **Календарь останется прежним:** 23.09.2026–31.12.2026. Перенос в облако не расширит диапазон дат — это отдельное изменение приложения.

Эти ограничения следуют из текущих [настроек запуска FastAPI](../backend/app/main.py), [загрузчика каталога](../backend/app/catalog.py) и [правил объяснений](api.md).

## Как я предлагаю обновлять каталог

Для начала достаточно обновления вручную, без автоматического опроса облака:

1. Сохранить новую версию отдельным файлом, например `catalog-2026-09-23-v2.csv`, оставив предыдущую.
2. Получить новую версию на сервер во временный файл.
3. Проверить её существующим валидатором проекта: структуру, обязательные поля, id, даты и происхождение.
4. Только после успешной проверки сделать её рабочей версией и перезапустить backend.
5. Проверить готовность каталога и один контрольный запрос; сохранить возможность вернуться к предыдущей версии.

Если загрузка или проверка не удалась, новая версия не должна затирать последнюю исправную. **Такой порядок обновления и автоматический откат пока не реализованы.** Сейчас ошибка чтения при старте приводит к HTTP 503, а не к автоматическому восстановлению старого файла.

Одинаковый файл нужно загружать без пересохранения через редактор таблиц, если цель — только перенос. Для производного JSONL необходимо переносить и соответствующий `.meta.json`; рабочим источником выбирается либо CSV, либо JSONL, без объединения двух копий одного каталога.

## Когда стоит перейти от CSV к базе данных

CSV подходит, пока каталог меняет один человек и обновления редкие. База данных становится полезнее, когда несколько людей одновременно редактируют профили, нужен кабинет подрядчика, частые изменения календаря или история изменений отдельных полей.

Это отдельное развитие проекта. Для размещения текущего каталога в облаке оно не требуется.

## С чего начать после выбора варианта

Нужно определить место размещения FastAPI, способ хранения файла — постоянный диск или отдельный bucket — и порядок обновлений. При выборе тарифа учитывайте стоимость работающего backend, хранения, запросов и передачи данных: небольшой размер CSV сам по себе не означает бесплатную работу всего сайта.

Для быстрого первого запуска мой выбор — **постоянный диск рядом с FastAPI**. Для независимого хранения и регулярного обновления файла — **приватный bucket и загрузка проверенной версии перед стартом сервера**. Здесь описан только план; подключения и публикации не выполнялись.
